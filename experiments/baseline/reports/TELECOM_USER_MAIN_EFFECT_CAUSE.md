# 为什么 GPT-5.2 user 比 Sonnet-4.6 user 更容易拿高 performance

**数据**: telecom 域,2×2 = {GPT-5.2, GPT-5.4} agent × {GPT-5.2, Sonnet-4.6} user,均 high reasoning,seed 300,3 trials,每格 N=342(已补齐缺失 2 条)。

## 0. 现象(主效应,远比 flip 稳健)

| | 5.2 user | S4.6 user | 主效应 |
|---|---|---|---|
| GPT-5.2 agent | 89.18% | 86.84% | −2.34pp |
| GPT-5.4 agent | 93.27% | 83.04% | −10.23pp |
| **两 agent 平均** | **91.2%** | **84.9%** | **−6.3pp** |

agent 面对 5.2 user 一致更高。**两个 agent 都成立** → 这是 user simulator 的主效应,不依赖 flip 的显著性。

## 1. 失败几乎全在 user 侧,agent 侧两边完全一样

reward 拆成 user 侧(用户要把设备弄到正确终态)vs assistant 侧(agent 自己的工具调用),做 sim 级失败归因:

| 失败归因 | 5.2 user | S4.6 user | Δ |
|---|---|---|---|
| 总失败 | 60 (8.8%) | 103 (15.1%) | **+43** |
| **USER 侧 only** | 42 | 81 | **+39** |
| **ASSISTANT 侧 only** | 5 | **5** | **0** |
| both | 13 | 17 | +4 |

**S4.6 多出的 43 个失败,~39 个(91%)是纯 user 侧;agent 自身失败两边一字不差(5 vs 5)。**
→ agent 干得一样好,差距完全来自 user simulator 没把设备修到工作状态。

> 注:per-assertion 看 `action_assistant` 有 −4.6pp,但 ACTION 几乎不在 `reward_basis` 里(基本全是 ENV_ASSERTION),所以不计入 reward,assistant 侧的 reward 失败才会两边相等。

## 2. 失败模式:几乎全以"转人工"收尾(更正)

> **更正**:初版写成"用户假完成提前喊停"是错的。`termination_reason=user_stop` 把 `###STOP###/###TRANSFER###/###OUT-OF-SCOPE###` 三种 token 混为一谈(见 `user_simulator.py:219` 的 `is_stop`),且对 **所有 684 sim 都成立**(成功的也以用户发 token 收尾),没有区分力。真正有区分力的是**具体 token**,重测后结论反转。

按 **user-side 失败 sim 的实际结尾 token**:

| 结尾 token | 5.2 user | S4.6 user |
|---|---|---|
| **###TRANSFER###**(agent 转人工) | 47% | **97%** |
| ###STOP###(以为完成) | 40% | 1% |
| ###OUT-OF-SCOPE###(放弃) | 13% | 2% |
| 失败最多的 env_user assertion | `assert_can_send_mms` ×37 | `assert_can_send_mms` ×73(翻倍) |
| user-fail sim 长度(中位) | 23 user-turn | **32 user-turn** |

**S4.6 的失败几乎全是 agent 主动 `transfer_to_human_agents` → 用户回 ###TRANSFER###(97%)**,此时设备没修好 → env_user 终态失败。5.2 的失败则是转人工/假完成各半。注意:转人工这个**动作由 agent 发起**,但导致的是 user 侧设备终态不达标——我的"user 侧归因"按断言的 `env_type` 分,衡量的是"**哪个条件没达成**"(设备状态),不是"谁造成的"。S4.6 失败时对话还**更长**(中位 32 vs 23 轮)——绕更多轮仍走到转人工。

## 3. 集中在多步任务(MMS)

| issue 类型 | 5.2 user | S4.6 user | gap |
|---|---|---|---|
| **mms_issue** | 86.7% | 75.2% | **−11.6pp** |
| service_issue | 90.8% | 87.9% | −2.9pp |
| mobile_data_issue | 97.7% | 95.8% | −1.9pp |

按故障数:步骤越多惩罚越大(7 faults −16.7pp、6 faults −10.6pp)。MMS 任务捆绑最多设备故障(APN/存储权限/SIM/数据模式…),需要最多步骤。

## 4. 精确机制:走到转人工时设备尚有步骤未完成

- `action_user`(用户做的单个 device 动作)两边几乎相同(95.2% vs 94.4%)——**做过的动作是对的**。
- `env_user`(设备终态)差 −5.4pp——**终态不对**。
- 失败 sim 留下未达成的 device 终态:5.2 user 97%、S4.6 user 100%(基本是"没到工作状态"的二元失败)。

自洽解释:**走到转人工(或喊停)那一刻,全套必需 device 步骤还没做完——做过的步骤都对,但缺了关键的最后几步。** 缺的步骤不会体现在 action_user 不匹配上(没有对应调用可比),但会让 env_user 终态失败。

## 5. 为什么 S4.6 让 agent 转人工 ~6x(已验证)

**mms 任务转人工率:S4.6 24% vs 5.2 4%(6 倍)**,但用户做的修复动作数几乎一样(distinct write 5.02 vs 4.91)→ 不是 S4.6 做得少。

逐故障覆盖率(故障 token 直接编码在 task_id 里,是 ground truth):

| cohort | avg 故障数 | avg 修复数 | 覆盖率 | 遗漏 |
|---|---|---|---|---|
| 5.2 PASS | 4.9 | 4.1 | 84% | 基本无 |
| S4.6 TRANSFER 失败 | 5.6 | 4.0 | 71% | **~1.6 个/sim** |

S4.6 转人工集中在**更高故障数**的任务上,绝对修复数差不多(~4)但**留 ~1.6 个故障没修**,agent 验证到 `can_send_mms` 仍 false 就转人工。5.2 的转人工(仅 13 个)原因谱相同,只是频率低 6 倍。

### 根因:渐进/不充分披露(自然实验确认)

| | 5.2 user | S4.6 user |
|---|---|---|
| roaming 故障任务,用户**主动说"我在国外"** | **100%** | **85%** |
| → agent 执行 `enable_roaming` | 64% | 57% |
| 流量超额(agent 用工具可自查),agent `refuel_data` | 97% | 95% |

**关键对照**:只有"在国外"这种**只能由用户主动披露**的上下文出现缺口(100%→85%),agent 对应修复也少;而"流量超额"这种 **agent 自己查得到**的故障两边无差(97%≈95%)。→ 缺口来自 **user 没把关键上下文交给 agent**,不是 agent 能力。加上 S4.6 一次一个动作 + 询问"先做哪个"的拖沓风格(转录可见),在高故障任务上更难把所有故障覆盖完。

### 这个机制占多少失败(直接因果切分)

把 abroad-故障任务按"用户是否主动披露在国外"切开,量化它对失败的贡献:

| | 5.2 user | S4.6 user |
|---|---|---|
| abroad-故障任务总数 | 384 | 384 |
| 主动披露(失败率) | 384 (9.1%) | 352 (10.8%) |
| **未披露(失败率)** | **0** | **32 (100%)** |

S4.6 这 32 个"未披露"的 sim,经核验**不是退化对话**:中位 34 轮(正常)、故障中位 6 个、31/32 以转人工收尾;但 agent 只问过 2/32 的位置、`enable_roaming` **0/32**——roaming 终态必然挂,是**充分原因**。

反事实归因(若 S4.6 也像 5.2 那样 100% 披露,这 32 个按披露组 10.8% 失败率):

| 口径 | 数值 |
|---|---|
| 归因失败数 | **~28.5** (= 32 − 32×10.8%) |
| **占全部 S4.6 失败 (103)** | **27.7%** |
| **占超出 5.2 的额外失败 (43)** | **~66%** |
| 非披露 vs 披露失败率差 | **+89.2pp** (100% vs 10.8%) |

**"用户不主动说在国外"这一个披露缺口,解释了 S4.6 约 28% 的总失败、约 2/3 的额外失败。** 这是唯一能干净测量的纯披露依赖故障(roaming);剩余 ~1/3 额外失败来自"披露了仍失败"的多故障任务(覆盖/吞吐不足,见上)。

### LLM judge 复核(gpt-5.2 读全部 163 条失败,纠正归因口径)

用 gpt-5.2 对每条失败 sim 读完整转录 + ground-truth 故障 + 失败断言,中立分类首要根因(脚本 `scripts/judge_failure_cause.py`):

| 首要根因 | 5.2 user | S4.6 user | 超出 |
|---|---|---|---|
| A 用户隐瞒只有自己知道的上下文 | 0 | 5 | **+5** |
| B agent 没修完就转人工/放弃 | 57 | 97 | **+40** |
| C/D agent 出错 / 用户拒做 | 0 | 0 | 0 |
| E 其他 | 3 | 1 | −2 |

**关联视角**:失败中"有 roaming 故障且用户没说在国外"的数量 = S4.6 **41** vs 5.2 **0** → **43 个额外失败里 41 个(95%)共现于此机制**(LLM 检出的非披露 41 > 正则 32,关联更强)。

**调和**:这 41 个里 judge 把 36 个判成 B(因为 **agent 本可主动问"你在国外吗"**——核验:这些 case agent 只问 ~2/32 次、`enable_roaming` 0 次),只 5 个判成 A(纯用户隐瞒)。

**结论修正(重要)**:
- **关联层面**:~95% 的额外失败共现于"用户没披露在国外"——区分 S4.6 与 5.2 的变量确实是非披露。
- **因果归因层面**:这是 **user×agent 联合失败**(用户不主动说 + agent 不问 + 提前转人工),**纯由用户隐瞒、agent 无从知晓**的只占额外失败 ~12%(5/43),而非我此前结构化估的 ~66%。此前把**关联**当成了**因果归因**,LLM 复核予以纠正。
- 与披露无关的纯覆盖失败两边几乎相同(B 中 abroad=na/yes:S4.6 61 vs 5.2 57,仅 +4)→ 额外失败几乎全集中在"非披露"那一支。

### majority@5 反事实复判(事实锚定,定方向)

**事实(已核 telecom 源码)**:`is_abroad` 在 user 侧(`user_tools.py`/`surroundings`);agent 的 `TelecomTools` **没有任何读位置的工具**,只能 `enable_roaming`(写);**没有任何诊断会输出"在国外"**(症状只是"都正常但没数据")。→ **agent 获知"在国外"的唯一途径 = 用户主动说,或 agent 直接问。**

对 41 个 abroad-非披露失败做 majority@5(gpt-5.2,5 个温度),prompt 内写明上述事实防止幻想工具:

| majority@5(41 case) | 结果 |
|---|---|
| roaming 是真实阻塞原因 | **41/41** |
| 用户主动说了在国外 | **0/41** |
| agent 问过位置 | **1/41** |
| 归因 | **agent 从没问 40 / 用户隐瞒 1** |
| 投票一致性 | **41/41 全票一致** |

**最终调和(两个问题,两个答案,都对)**:
- **"每条失败该怪谁"**:怪 agent——它有唯一手段(问)却 40/41 从没问过。不是用户恶意隐瞒。
- **"为什么 S4.6 比 5.2 差"**:差在**用户主动披露行为**。agent"不主动问位置"这个习惯在两种 user 下是**常量**;5.2 user **100% 主动说**在国外 → agent 不问也拿到了 → 开 roaming → 过;S4.6 user **不主动说** → 把 agent"不问"的短板暴露出来 → roaming 没开 → 败。
- 因此:**区分两个 user 的变量 = 用户是否主动披露;失败之所以发生的机制 = agent 不靠问去补**。这是 user×agent 交互效应,不是单方面归因。

## 结论(因果链)

```
S4.6 user 的行为特征(已知大样本事实):
  渐进式披露(关键上下文不主动交) + 一次只做一个 device 动作 + 拖沓询问"先做哪个"
        │
        ▼
agent 拿不到只能由用户披露的上下文(如"我在国外":100%→85%)→ 漏做对应修复
(对照:agent 自己查得到的故障如流量超额,两边无差 97%≈95%)
        │
        ▼
高故障 MMS 任务上覆盖率 84%→71%,平均留 ~1.6 个故障没修
        │
        ▼
agent 验证到 can_send_mms 仍 false、"无法在范围内解决"→ transfer_to_human_agents
(S4.6 mms 转人工率 24% vs 5.2 的 4%,6×;失败 97% 以 ###TRANSFER### 收尾)
        │
        ▼
env_user 终态断言失败 → reward=0 —— 而 agent 侧 reward 失败两边完全相同(5 vs 5)
        │
        ▼
S4.6 user 下 agent pass rate 系统性低 6.3pp
```

**一句话**:不是 agent 在 S4.6 user 下变弱了(agent 侧 reward 失败两边相同),而是 **S4.6 user 渐进披露、把只有自己知道的关键上下文藏着不交给 agent**,导致 agent 在多步设备任务上漏修故障、最终转人工收尾,设备终态没修好 → 终态检查失败。GPT-5.2 user 一上来就把信息倒给 agent,所以 agent 更容易把所有故障覆盖、修好。

> **方法论教训**:不要用 `termination_reason=user_stop` 作判据——它把 STOP/TRANSFER/OUT-OF-SCOPE 混在一起且对所有 sim 都成立。要扫最后一条 user 消息的**具体 token**。
